# Pairing with AutoFixture

`Xfty.AutoFixture` is a separate, opt-in package - core `Xfty` has no
dependency on AutoFixture, and never will. It closes the gap described in
[reference/comparison.md](../reference/comparison.md#could-xfty-pair-with-one-of-these-to-close-a-gap):
AutoFixture's model is "fill in everything, then tell me what you
overrode"; XFTY's is "declare everything you care about, generate the rest
of the graph." The two compose in **two independent, non-mutually-exclusive
ways**.

```bash
dotnet add package Xfty.AutoFixture
```

## 1. Point AutoFixture at a RecordProvider

`fixture.Create<T>()` normally builds `T` from AutoFixture's own recursive
auto-property population, which knows nothing about XFTY's relationships,
shared ancestors, or cycle guards. `XftyCustomization` intercepts requests
for any type with a Provider registered in your `IProviderLookup` and
answers them with a real, fully-formed XFTY-generated record instead:

```csharp
using AutoFixture;
using Net.Nowhereatall.Xfty.AutoFixture;

IFixture fixture = new Fixture()
    .Customize(new XftyCustomization(lookup));

Contact contact = fixture.Create<Contact>();
// contact.AccountId is set - the required Account relationship was
// generated by XFTY, not left null the way RecordProvider's own default
// inclusivity would leave it.

List<Contact> contacts = fixture.CreateMany<Contact>(3).ToList();
```

Anything requested that XFTY has no Provider for - `string`, `int`, your
own unrelated types - falls straight through to AutoFixture's normal
generation. Nothing about this changes how you use `IFixture` for anything
else.

**Defaults, and why they differ from `RecordProvider`'s own:**

- `insertMode` defaults to `InsertMode.Mock` - in-memory Ids, no real DML,
  matching AutoFixture's own offline scope.
- `inclusivity` defaults to `InsertInclusivity.Required` - **not**
  `RecordProvider`'s own default of `None`. AutoFixture users expect
  `Create<T>()` to hand back a complete object; leaving every required
  relationship null because nothing asked for it explicitly would surprise
  anyone coming from AutoFixture's side of this pairing.

Override either default explicitly - here, back to `RecordProvider`'s own
defaults instead of the ones tuned for AutoFixture:

```csharp
IFixture fixture = new Fixture().Customize(
    new XftyCustomization(lookup, InsertMode.Mock, InsertInclusivity.None));

Contact contact = fixture.Create<Contact>();
// contact.AccountId is null again - nothing asked for the relationship explicitly.
```

`InsertMode.Now` works the same way (with
`RecordProvider.SetPersistenceGateway(...)` configured on the Providers
involved) for a customization that should insert for real instead of
mocking Ids.

This is deliberately a thin `ISpecimenBuilder` - if it needs to work
differently for some request (a specific variant key, a per-call override
template), build that Contact yourself with `RecordProvider`/
`RecordProvider<TRecord>` directly instead of through the fixture; nothing
requires every record in a test to come from the same path.

## 2. Let AutoFixture fill in what a Provider left unset

The inverse pairing: generate a record the normal XFTY way - Master
Template, override template, relationships, everything you actually
declared - and hand AutoFixture only the fields *nothing* touched.

```csharp
using AutoFixture;
using Net.Nowhereatall.Xfty.AutoFixture;

IFixture fixture = new Fixture();
Account account = (Account)await new RecordProvider(typeof(Account), lookup)
    .SetInsertMode(InsertMode.Mock)
    .SetUnsetFieldFiller(new AutoFixtureUnsetFieldFiller(fixture))
    .Supply();

// account.Name/.Industry/... are exactly what AccountDataProvider declared.
// account.NumberOfEmployees, .AnnualRevenue, .Site, ... - fields the
// Master Template never mentions at all - now hold real AutoFixture values
// instead of null.
```

`RecordProvider<TRecord>` (the generic wrapper) has the same
`SetUnsetFieldFiller(...)`, and it applies to every record a `Supply*()`
call generates, including ancestors pulled in along the way - each against
its own Provider's own unset fields, not just the top-level record's.

**What counts as "unset":** a field with no default value, no override
template value, no `Put(...)`, and no required/optional relationship on
it - not a field XFTY resolved *to* `null` or some other value on purpose.
`IUnsetFieldFiller` (the extension point this is built on, in core `Xfty`)
runs after every one of XFTY's own value/relationship passes, so it never
fights a Provider for a field the Provider actually cares about, and before
`InsertMode.Now` hands the record to a real database - a NOT NULL column
XFTY itself never bothered filling still gets something.

### Excluding specific fields

Most commonly needed for **navigation-shaped properties** - a
bundle-enrichment convenience like `Contact.Account`/`Account.Contacts`,
populated only by `Bundle.Inject(...)`/`InjectAll` (see
[enrichment.md](enrichment.md)), never by any Master Template. Nothing
about the Master Template distinguishes "a scalar field nothing set" from
"a navigation property enrichment populates separately" - both look
identical to `IUnsetFieldFiller`, so left alone, this filler will
dutifully hand `Contact.Account` a fake, unrelated `Account` neither the
template nor an enrichment pass asked it for. If you enrich navigation
properties afterward, this is harmless - `BundleEnricher` returns *new*
instances, so the AutoFixture-filled value on the original never survives
into what enrichment hands back - but it's wasted generation, and if you
*don't* enrich, that fake value sticks around on the returned record. Opt
the specific properties out:

```csharp
AutoFixtureUnsetFieldFiller filler = new AutoFixtureUnsetFieldFiller(fixture)
    .Excluding(Field.Of<Account>(x => x.Contacts))
    .Excluding(Field.Of<Account>(x => x.Parent))
    .Excluding(Field.Of<Account>(x => x.ChildAccounts));
```

### Circular / unsatisfiable fields never propagate an exception

A field can genuinely circle back on its own type (`Account.Parent` is
`Account`). Resolving it through AutoFixture's default engine can trip its
`ThrowingRecursionBehavior`, raising `ObjectCreationException` deep inside
`Fill`. This filler catches exactly that exception and leaves the field
precisely as XFTY left it (`null`, typically) - it never lets a recursive
field abort the whole `Supply()` call. If you'd rather AutoFixture return
an omitted value for those fields instead of relying on this catch, install
`OmitOnRecursionBehavior` on the fixture in place of the default:

```csharp
fixture.Behaviors.Remove(fixture.Behaviors.OfType<ThrowingRecursionBehavior>().Single());
fixture.Behaviors.Add(new OmitOnRecursionBehavior());
```

Either way, no field this filler cannot satisfy ever surfaces as an
exception from `Supply()`.

## Combining both

Nothing stops one fixture from doing both jobs - XFTY resolves the graph,
AutoFixture fills whatever scalars are left:

```csharp
IFixture fixture = new Fixture().Customize(new XftyCustomization(lookup));

Contact contact = (Contact)await new RecordProvider(typeof(Contact), lookup)
    .SetInsertMode(InsertMode.Mock)
    .SetInclusivity(InsertInclusivity.Required)
    .SetUnsetFieldFiller(new AutoFixtureUnsetFieldFiller(fixture))
    .Supply();

// contact.AccountId - XFTY's own relationship resolution.
// contact.Birthdate - ContactDataProvider never configures this; AutoFixture did.
```
